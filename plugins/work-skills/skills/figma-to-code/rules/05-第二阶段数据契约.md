# 第二阶段数据契约

执行第二阶段时与 `03-公共状态契约.md` 一起读取。本文件定义 `stage-2-handoff.json` 的 `handoff` 内容和独立 `asset-manifest.json`。

## A1 补读报告

```json
{
  "handoff": {
    "reread_rounds": [
      {
        "round": 1,
        "targets": [],
        "resolved_fields": [],
        "remaining_fields": [],
        "source_changes": [],
        "confidence_changes": [],
        "readiness_after_round": 0,
        "blocking_reasons": []
      }
    ],
    "field_source_confidence": [],
    "design_analysis_updates": [],
    "readiness_after_reread": 0,
    "classification_changes": [],
    "asset_manifest": {
      "path": "asset-manifest.json",
      "sha256": "",
      "asset_count": 0,
      "qa_pass_count": 0,
      "qa_fail_count": 0
    },
    "asset_qa_summary": [],
    "remaining_risks": [],
    "blocking_reasons": [],
    "can_enter_stage_3": false
  }
}
```

`design_analysis_updates` 只记录相对第一阶段新增或修正的字段及证据；不复制未变化的整份分析。`classification_changes` 记录图层从旧分类到新分类的原因。`asset_manifest` 是规范 manifest 的路径、哈希和统计摘要，完整资产事实只写入 `asset-manifest.json`，并同时列入公共外壳的 `output_artifacts`。

## A2 Asset manifest

```json
{
  "asset_manifest": {
    "run_id": "",
    "frame_id": "",
    "assets": [
      {
        "asset_id": "badge-title-visual",
        "file": "../../../src/assets/badge-title-visual@3x.png",
        "source_layer_ids": [],
        "content_layers": ["badge", "rays", "art-text"],
        "excluded_layers": ["code-background"],
        "asset_type": "complex_visual_group",
        "format": "png",
        "scale": 3,
        "transparent": true,
        "logical_bounds": { "x": 0, "y": 0, "width": 100, "height": 50 },
        "visual_bounds": { "x": -5, "y": -6, "width": 110, "height": 62 },
        "export_canvas_bounds": { "x": -8, "y": -8, "width": 116, "height": 66 },
        "pixel_size": { "width": 348, "height": 198 },
        "safe_padding": { "top": 8, "right": 8, "bottom": 8, "left": 8 },
        "placement": { "section": "hero", "x": -8, "y": -8, "width": 116, "height": 66 },
        "source_strategy": "figma_export | raw_image | cleaned_svg | approved_fallback",
        "transparent_treatment": "native_alpha | remove_injected_svg_rect | matte_match | color_key_last_resort",
        "user_override": "勋章、光芒、艺术字整体切图，底板背景用代码",
        "sha256": "",
        "qa": {
          "decode": true,
          "dimensions": true,
          "alpha": true,
          "bounds": true,
          "safe_padding": true,
          "ratio": true,
          "content": true,
          "excluded_content_absent": true,
          "hash_recorded": true
        },
        "visual_qa": {
          "status": "pass | fail",
          "evidence": ["qa/stage-2-asset-contact-sheet.svg", "figma-reference.png"],
          "notes": ""
        },
        "qa_report": "qa/stage-2-asset-qa.json",
        "qa_status": "pass | fail"
      }
    ],
    "blocking_reasons": []
  }
}
```

`source_strategy=approved_fallback` 或 `transparent_treatment=color_key_last_resort` 时必须附证据、风险和不可约扣分。

`file` 和 `qa_report` 相对 `asset-manifest.json` 所在的 `run_dir`；正式资产可用 `../../..` 引用 `delivery_root` 的仓库资产目录。`qa_report` 保存机器 QA；`visual_qa` 保存逐项视觉结论。`qa_status=pass` 仅在二者都通过，且 `qa` 的内容、排除项、边界、比例和哈希检查全为 `true` 时成立。默认所有资产引用同一份 `qa/stage-2-asset-qa.json`，其中每个 `asset_id` 有唯一记录。

QA 报告中的 `file` 可保留候选临时路径和文件名；正式复制时允许改为稳定语义名。生成器以 `asset_id`、格式和 SHA-256 绑定候选 QA 与正式资产，不比较 basename。只有内容哈希或格式变化才需要重新执行机器 QA，纯重命名不得造成重复验证。

候选文件和逐资产临时 QA 只存在于 `/tmp/figma-to-code/<run_id>/stage-2-candidates/`。通过机器 QA 的正式资产进入 `delivery_root` 的仓库资产目录；`run_dir` 只持久化合并 QA、单一联系表、必要的定向复合证据，以及发生失败时的 `diagnostics/stage-2-asset-attempts.json`。失败日志记录失败策略和检查，不保存失败二进制副本。

完成第二阶段时先用 `asset-qa.mjs bundle` 合并 QA，再使用 `generate-stage2-handoff.mjs` 生成交接；默认不生成独立 `state.json`。随后用 `validate-handoff.mjs` 解析 `stage-2-handoff.json`、`asset-manifest.json`、正式资产和 QA，确认 `workflow_state.current_stage=2`、所有活动文件存在且哈希一致、逐项机器/视觉门禁与统计一致，且任何必需资产失败时 `can_enter_stage_3=false`。


## 响应式字段（仅启用时）

`handoff.responsive_plan_ready` 必须为布尔值；`responsive_reread_fields` 记录约束、锚点、换行、裁切和可伸缩区的补读结果。启用响应式但该字段为 false 时，`can_enter_stage_3` 必须为 false。
