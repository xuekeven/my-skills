# 公共状态契约

本文件只定义四阶段共享的状态、证据基元和失效记录。执行某一阶段时，另读该阶段自己的数据契约；字段不适用时保留并写 `null`、空数组和原因，区分未知、未读取、视觉推断与源节点无该属性。

## C0 统一交付 JSON

四阶段分别生成以下唯一规范交接文件：

| 阶段 | 文件名 | `stage_name` |
|---|---|---|
| 1 | `stage-1-handoff.json` | `read_and_plan` |
| 2 | `stage-2-handoff.json` | `replenish_and_export` |
| 3 | `stage-3-handoff.json` | `implement_design` |
| 4 | `stage-4-handoff.json` | `acceptance` |

文件必须是 UTF-8、可由 `JSON.parse` 直接解析的标准 JSON，不允许注释、尾逗号、Markdown 外壳或 YAML。四个文件共用下列顶层结构；各阶段契约只定义 `handoff` 内部字段：

```json
{
  "schema_version": 1,
  "artifact_type": "figma_to_code_stage_handoff",
  "stage": 1,
  "stage_name": "read_and_plan",
  "generated_at": "",
  "workflow_state": {},
  "timing": {},
  "input_artifacts": [
    {
      "artifact_type": "figma_reference",
      "path": "figma-reference.png",
      "sha256": "",
      "status": "active | invalidated | missing"
    }
  ],
  "output_artifacts": [],
  "handoff": {}
}
```

`stage` 必须等于 `workflow_state.current_stage`，文件名、`stage_name` 与阶段必须一致。`input_artifacts` 引用本阶段实际消费的上游交接、manifest、参考图或报告；`output_artifacts` 引用本阶段生成且仍有效的辅助文件。路径相对当前 `run_dir`，可用 `../../..` 引用 `delivery_root` 内的代码和正式资产；所有参与门禁的文件记录 SHA-256 和状态。大体积事实只保留一个规范文件，例如资产详情放 `asset-manifest.json`、diff 详情放 `stage-4-visual-diff-report.json`，阶段交接只保存路径、哈希、摘要和门禁结论。

用户指定或目标项目确定的目录是 `delivery_root`，不是证据平铺目录。固定 `run_dir=<delivery_root>/.figma-to-code/runs/<run_id>/`；代码和正式资产留在交付区，交接、参考图、截图、diff、QA、audit、诊断和计时进入 `run_dir`。用户说“输出到 test”即 `delivery_root=test`、`run_dir=test/.figma-to-code/runs/<run_id>`。每个阶段写完 JSON 后运行 `scripts/validate-handoff.mjs --file <stage-handoff.json>`；Stage 1 的节点覆盖专项检查已内置。随后停止 `handoff_generation` 计时。回复只返回摘要和交接文件路径，不再另写一份 Markdown/YAML 交接。

默认不生成独立 `state.json`，因为 `workflow_state` 已嵌入每个阶段交接；只为明确的旧消费者兼容时生成。默认不生成 `sections.json`，section 的规范来源是 `stage-1-handoff.json#handoff.design_analysis.layout_structure.sections`；读取器仍兼容旧版顶层 `design_analysis`。逐资产 QA 临时报告合并为 `qa/stage-2-asset-qa.json`；失败尝试日志仅在失败时写入 `diagnostics/`。

## C1 字段证据

每个关键字段或可审计项至少包含：

```json
{
  "value": null,
  "source": "figma_mcp_raw | targeted_mcp_reread | figma_final_visual_snapshot | visual_sampling_estimate | agent_visual_assist | manual_user_confirmation | unknown",
  "confidence": "high | medium | low | blocking",
  "evidence": [],
  "risk_note": "",
  "needs_confirmation": false
}
```

`agent_visual_assist` 表示当前执行者的视觉辅助推断，不限定模型、供应商或工具。估算值不能标 `high`，关键字段为 `low/blocking` 时不得使用 `generation_mode=normal`。

## C2 Audit item

```json
{
  "layer_id": "",
  "layer_name": "",
  "expected": "",
  "actual": "",
  "status": "pass | warn | error",
  "evidence": [],
  "risk_type": "none",
  "fix_strategy": "",
  "verification_result": ""
}
```

`status=error` 时 `fix_strategy` 必填。已解释的不可见、裁掉或布尔减除项必须给证据，不能通过删除 audit item 获得通过。

```json
{
  "workflow_state": {
    "run_id": "20260724T120000Z-file-frame",
    "status": "stage_1_planned | stage_2_assets_ready | stage_3_implemented | stage_4_validating | complete | blocked",
    "current_stage": 1,
    "input_type": "figma_node | figma_selection | screenshot",
    "figma_file_key": "",
    "frame_id": "",
    "frame_name": "",
    "frame_width": 375,
    "frame_height": 812,
    "source_image_sha256": null,
    "identity_verified_at": "",
    "generation_mode": "normal | generate_with_risk | blocked",
    "blocking_reasons": [],
    "timing": {},
    "timing_history": [],
    "active_artifacts": [],
    "invalidated_artifacts": [],

```

截图输入的 Figma 字段可为空，但 `source_image_sha256` 必填。Figma 输入必须有 file key、Frame ID 和尺寸。

## C4 阶段计时

每阶段使用墙钟时间记录实际耗时，不用估算值替代。`duration_ms` 是该阶段所有活动段之和；因等待用户、审批或外部状态而暂停的时间不计入。工具无法计时时保留已知字段并把状态标为 `partial`。

```json
{
  "timing": {
    "measurement_method": "workflow_timer | wall_clock_fallback",
    "timing_status": "complete | partial",
    "timer_file": "/tmp/figma-to-code/<run_id>/timing.json",
    "stage": 1,
    "stage_name": "read_and_plan",
    "started_at": "",
    "finished_at": "",
    "duration_ms": 0,
    "phase_durations_ms": {
      "rule_loading": 0,
      "design_read": 0,
      "handoff_generation": 0
    },
    "excluded_wait_ms": 0,
    "notes": []
  }
}
```

`workflow_state.timing` 保存当前阶段计时；跨阶段运行在 `timing_history` 或 `timing.json` 中累积。阶段交接至少显示总耗时和各 phase 耗时。计时本身不得成为绕过门禁的理由。

正常阶段使用 `workflow.mjs begin` 启动阶段和首个 phase，使用 `transition` 原子切换 phase，使用 `finish` 结束末 phase 和阶段。这样每个边界只写一次计时文件，并避免并发读改写覆盖事件。`start/stop` 只用于旧调用方兼容，以及暂停/恢复等待段；`summary` 发现任一必需 phase 缺失时必须保持 `timing_status=partial` 并列出缺失项。

## C5 转换与失效记录

```json
{
  "from": "stage_4_validating",
  "to": "stage_2_assets_ready",
  "reason": "asset_alpha_edge_clipped",
  "root_cause": "asset_export",
  "trigger_report": "visual-check/report-03.json",
  "affected_scope": ["badge-title-visual"],
  "invalidated_artifacts": ["preview.png", "diff.png", "visual-diff-report.json", "restore_fidelity"],
  "recovery_checks": ["asset_qa", "build", "screenshot", "diff", "affected_audits"],
  "timestamp": ""
}
```

回退后立即更新 `workflow_state.active_artifacts/invalidated_artifacts`。失效产物不得被最终报告引用；恢复后必须生成新哈希、截图、报告或分数。

## 需求模式兼容扩展

每个页面仍使用本文件的单 Frame 外壳和独立 run_id；不要向原生成器传多 Frame 数组。产品级需求、页面列表、功能结果和最终聚合门禁由 `09-需求驱动交互闭环.md` 及 `../references/需求契约与功能验收.md` 定义。此时页面级 `can_deliver` 不是产品最终结论。
