# 意图路由与兼容口令

本文件只在旧专项口令、自然语言意图不明确或多意图冲突时加载。请求已包含下表中的精确规范英文子命令时，直接按 `SKILL.md` 路由，不读取本文件。

`/figma-to-code` 是规范触发命令，调用格式为 `/figma-to-code <command>`。先匹配斜杠命令后的规范英文子命令，再加载对应阶段和契约。规范子命令是当前请求的最高优先级范围边界；其后的 Figma 链接、输出目录或泛化描述不增加阶段。

| 意图类 | 规范子命令与兼容表达 | 加载与执行 | 写入边界 |
|---|---|---|---|
| 三阶段闭环 | `implement three stages` | 依次执行阶段 1–3；完成页面实现和第三阶段交接，但不执行第四阶段完整视觉验收 | 按阶段开放写入；不得把第三阶段完成宣称为最终视觉验收通过 |
| 完整闭环 | `implement whole stages`；兼容 `【复杂落地页还原】`、`【复杂模块高还原】` | 依次执行阶段 1–4；进入每阶段前再加载该阶段契约 | 按阶段开放写入；不得提前越过门禁 |
| 读取与规划 | `read and plan`；兼容 `【读取当前画板】`、`【深度读取当前画板】` | 阶段 1 + 第一阶段契约 | 只读；不导出正式资产，不写页面 |
| 读取门禁与补读 | `【读取完整度检查】`、`【读取门禁检查】`、`【补读缺失字段】`、`【代理辅助补全读取】`；旧口令 `【Claude辅助补全读取】` 仅作为同义路由别名 | 阶段 1 的 P6–P8；必要时执行阶段 2 的定向补读，但不导出资产 | 只读设计；只更新分析/补读交接；输出统一使用通用名称 |
| 资产规划与 QA | `【切图分组规划】`、`【切图尺寸检查】`、`【复杂资产导出策略检查】` | 规划只读阶段 1 P5；检查已有资产时读阶段 2 A3/A7 | 规划不导出；检查不改资产；只有用户要求导出/修复时才写资产 |
| 补读并导出资产 | `replenish and export` | 阶段 2 + 第二阶段契约 | 可写正式资产、manifest 和 QA；不写页面 |
| 页面实现 | `implement the design` | 阶段 3 + 第三阶段契约；前置不可靠时按状态机回退 | 只写当前页面所需代码和引用，不验收即宣称完成 |
| 完整验收 | `acceptance the page`；兼容 `【机制化验收当前页面】`、`【复杂页面自查】`、`【循环截图验收】`、`【再次验收默认状态】`、`【多维还原度评分】` | 阶段 4 + 第四阶段契约 | 可按根因做局部修正并复验；禁止整页重构 |
| Diff 只读 | `【生成视觉差异报告】`、`【Diff 尺寸对齐检查】` | 阶段 4 V1–V3 + 第四阶段契约 | 只生成截图、捕获报告和 diff 报告；不修改页面 |
| 专项审计 | `【元素覆盖率检查】`、`【卡片效果专项检查】`、`【富文本片段检查】`、`【层级和背景插图检查】`、`【嵌套模糊形状检查】`、`【微元素位置检查】`、`【按钮图标检查】`、`【描边文字检查】`、`【文字折行检查】`、`【检查复杂图层还原】`、`【混合模式与透明度检查】`、`【渐变方向检查】`、`【特殊字体片段检查】`、`【角标锚点检查】` | 阶段 4 对应 audit；需要源字段时只回退到最小补读范围 | 默认只读并输出 finding；没有明确“修复”不得改代码或资产 |
| 局部修复 | `【只修当前问题】`、`【按问题清单修正】`、`【按差异报告局部修正】` | 读取指定 finding/报告和负责阶段的最小规则 | 只修改清单中的区域；修改后复验受影响项和回归，不扩展范围 |
| 轻交互 | `【轻交互检查】`、`【补齐轻交互】` | 检查读阶段 3 I8/阶段 4；补齐执行阶段 3 I8 | “检查”只读；“补齐”仅实现已有 inventory，不能改变静态默认态 |
| 规则维护 | `【更新规范】` | 仅在用户明确要求修改 Skill 时执行 | 只改 Skill 规则/脚本及其测试，不触碰业务页面 |

只收到 `/figma-to-code` 而没有规范子命令时，列出六个规范子命令并等待选择，不执行任何阶段。出现多个相互冲突的规范子命令时先确认，不自动组合或升级为完整闭环。

自然语言同义表达使用相同边界；未列出的新表达按语义归入最接近的意图类，并在执行前声明写入边界。`Implement this design from Figma` 等泛化模板句不等于 `implement whole stages`，也不能覆盖已识别的单阶段子命令。口令名称不授予额外权限；用户在当前消息中的明确范围始终优先。

## 需求文档路由

六个规范命令均可附带需求文档；按 `09-需求驱动交互闭环.md` 启用需求模式，但不扩大阶段边界。read and plan 只做需求契约、页面设计规划和问题清单，不写应用。implement whole stages 才执行产品完整闭环。需求已明确的业务交互不受“轻交互”兼容入口的默认范围限制。
