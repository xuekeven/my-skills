# 第三阶段数据契约

执行第三阶段时与 `03-公共状态契约.md` 一起读取。本文件定义 `stage-3-handoff.json` 的 `handoff` 内容。

```json
{
  "handoff": {
    "preview": {
      "route_url": "http://localhost:5173/restored-page",
      "route_path": "/restored-page",
      "capture_target": "[data-figma-frame]",
      "expected_css_size": { "width": 375, "height": 812 },
      "default_interaction_state": {}
    },
    "changed_files": [],
    "used_asset_ids": [],
    "implementation_mapping": {
      "real_text_layers": [],
      "code_css_layers": [],
      "svg_layers": [],
      "png_layers": []
    },
    "checks": [
      { "name": "build", "command": "", "exit_code": 0, "result": "pass | fail | not_applicable", "reason": "" }
    ],
    "runtime_errors": [],
    "known_risks": [],
    "blocking_reasons": [],
    "can_enter_stage_4": false
  }
}
```

不允许只写“检查通过”；每项记录实际命令、退出码和证据。`capture_target` 必须是可由浏览器查询的唯一 CSS selector，供第四阶段机器测量和精确截图使用。

`input_artifacts` 至少引用有效的 Stage 1、`stage-2-handoff.json` 与 `asset-manifest.json` 及其哈希；`output_artifacts` 列出 `delivery_root` 内的实现文件，以及 `run_dir` 内的 `stage-3-preview.png` 与 `stage-3-capture-report.json`。所有 artifact 和 `changed_files` 最终统一为相对 `run_dir` 的路径。实现特有字段先写入 `/tmp/figma-to-code/<run_id>/stage-3-input.json`，再使用 `scripts/generate-stage3-handoff.mjs --delivery-root <delivery_root>` 生成正式交接，不把该临时输入保留为正式产物。Stage 4 只能只读复用这两个证据文件；需要重拍时必须使用 Stage 4 前缀，禁止覆盖后造成 Stage 3 历史哈希失效。

生成器和校验器必须独立确认：所有 `changed_files` 存在且列入输出产物；`used_asset_ids` 覆盖 manifest 正式资产且 QA/哈希通过；实现分类对 Stage 1 可见图层全集无重复、遗漏或额外项；捕获 URL、selector、尺寸、截图哈希、网络、控制台与运行时通过；适用检查无失败。任一条件不满足时 `can_enter_stage_4=false`。

`route_url` 可以是已运行服务的 `http(s)` URL，也可以是纯静态页面的绝对 `file://` URL。没有可用服务且页面无法以 `file://` 运行时记录 `preview_service_not_running`；不得自行启动服务或伪造捕获产物。


## 响应式字段（仅启用时）

`handoff.responsive_validation` 保存响应式子门禁的路径、哈希、基准宽度回归摘要和 `can_deliver`。`layout_mode=fixed_and_responsive` 且该门禁未通过时，`can_enter_stage_4` 必须为 false。
