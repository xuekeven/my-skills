# 给需求驱动 Skill 的输入

沿用 `/figma-to-code` 的规范命令，不必另学新的调用方式。当前有单阶段命令、三阶段闭环命令和四阶段闭环命令；需求文档模式下通常使用 `implement whole stages` 完成视觉与功能验收。例如：

```text
/figma-to-code read and plan
请读取附件需求文档，提取本期范围、页面与设计稿对应关系、交互和状态、数据模型、验收用例以及冲突问题。只做规划。
目标项目：<项目绝对路径>
需求文档：<文件绝对路径>
```

```text
/figma-to-code implement whole stages
按照附件需求及其中的设计稿，在 <项目绝对路径> 实现可交互页面，并进行视觉和功能验收。
接口尚未提供，允许使用 mock 数据，但需要页面间数据一致。先列出会影响主流程的需求冲突。
```

需要启动服务时，在请求中明确“允许启动本项目预览服务进行验收”；是否保留服务另行说明。使用 `implement three stages` 时只执行 Stage 1–3，不包含第四阶段视觉验收、跨页面功能回归、产品聚合验收或最终 `ui-ux-report.md`。

## 建议的文档结构

不强制改变现有 DOCX 格式。重要的是明确“展示内容”和“本期行为”的区别：

1. **范围**：本期做什么、不做什么；“不做”是隐藏、禁用，还是保留外观点击无反应。
2. **页面与设计稿**：每页名称、带 node-id 的设计链接、默认状态；弹窗或其他状态有设计则逐项列出。
3. **流程**：从哪页哪个入口，到哪页，传什么参数，返回到哪、是否保留选择。
4. **交互表**：页面 / 控件 / 触发 / 前置条件 / 状态与数据变化 / 可观察反馈 / 本期状态。
5. **数据与时间**：API 或允许 mock、字段样例、日期时区、当前周定义、倒计时算法、刷新与持久化规则。
6. **边界**：加载/空/失败/重试、无效路由参数、重复操作；仅列适用的情况。
7. **验收用例**：Given 初始数据，When 操作，Then 期望结果。
8. **待确认项**：缺设计、冲突的范围、未确定业务规则，避免写成已确认结论。

## 附件“AI一对一”的分析示例

这是范围识别示例，不是所有任务的固定业务规则。文档本身不随 Skill 打包，也不包含其设计稿图像。

| 页面 | 设计节点 | 本期应实现/保留 |
|---|---|---|
| 学习计划首页 | `513:1170` | 开始学习 → 对应课程页；调整时间 → 安排页并定位本周；默认当前周、课程卡片与课次数量 |
| 课程学习页 | `514:1489` | 返回首页；对应课程信息；动态剩余分钟；测评和右侧专项保留外观，点击无反应 |
| 本周课次安排页 | `515:2663` | 返回首页；按学科展示本周课次；新增/调整/删除按钮点击无反应 |

三个节点来自同一个文档内 Figma 文件；实际执行仍需核验文件 key、节点、尺寸和权限，示例不能替代设计读取。

需要记录的范围判断：

- 首页“学习计划一览”明确不做，不能实现新总览页。
- 安排页目标写“支持新增、调整和删除”，但本期交互明确无反应；不应额外开发 CRUD、表单、删除确认。
- 文档明确二、三页顶部返回，因此“任何按钮不做”按具体返回规则的特例理解并记录依据；若用户另有意思再确认。
- 首页“周计划横向切换区域”与“暂不考虑点击别处”有歧义：展示区域可还原，但是否允许周切换要确认，不默认为一定要做或完全不做。
- “增加课次”仅要求展示、且其他点击排除，先保留无反应，不编造入口流程。
- “调整时间”进入安排页是本期行为，不等于安排页里的改期操作也要实现。
- 动态剩余分钟明确要求，但取整、时区、课后显示和数据来源未明确：提出可确认约定，而非固定写死“X 分钟”。

示例验收：点击不同课程进入对应课程页；调整时间进入当前周安排；两页返回首页；推进测试时钟后剩余时间变化且结束边界不为负；点击测评/新增/删除不跳转、不修改数据、不弹提示。是否做周切换及其用例随澄清结果更新。
