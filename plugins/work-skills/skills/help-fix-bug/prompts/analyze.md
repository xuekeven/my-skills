# 分析bug

## 新建分支

使用仓库内脚本 **`tools/create-branch.mjs`** 从 comprehend 阶段的 `bug_appear_baseline` 创建修复分支。不要手写 `git checkout -b` 去猜分支名——脚本会以**执行时**的本机时间自动生成 `fix-${YYMMDD}-${HHmm}`（如 `fix-260423-2223`）并完成切换。

### Agent 执行要点

在目标仓库根目录执行，或通过 `GCL_REPO_ROOT` / `--cwd` 指定仓库根目录：

```bash
node tools/create-branch.mjs --base "${bug_appear_baseline}"
```

- `--base`：传入 `bug_appear_baseline`（branch / tag / commit / `origin/…`；形如 `1.2.5` 的版本号仅当仓库存在对应 tag 时有效，详见脚本注释）。
- 基准只在远端、本地解析失败时：先加 `--fetch`。
- 工作区有未提交修改必须继续时：加 `--allow-dirty`。
- 仅预览命令不实际建分支：加 `--dry-run`。

执行成功后准备在新分支上做分析与修改。

分支名说明：

- 在执行 `tools/create-branch.mjs` 之前，不要声称已经知道真实分支名。
- 开始执行前，只能说明分支名将由脚本按 `fix-YYMMDD-HHmm` 格式自动生成。
- 执行完成后，必须从脚本 stdout 的 `已创建并切换到分支: ${actual_fix_branch}`，或从 `git branch --show-current` 读取真实分支名，记为 `actual_fix_branch`。
- 对用户输出成功信息时，必须使用 `actual_fix_branch`，不要输出 `fix-YYMMDD-HHmm`、`fix-${实时年月日}-${实时时分}` 这类格式占位符。

### 用户交互

开始执行前，输出模板：

```
现在开始分析 bug。首先从 ${bug_appear_baseline} 新建一个由脚本自动命名的 `fix-YYMMDD-HHmm` 分支，在该分支上分析和修复代码。
```

执行完成后，输出模板：

```
新建 ${actual_fix_branch} 分支成功！
```

## 分析链接

若 `bug_user_desc` 当中含有**报告链接**（先不处理产品链接），需要拿到链接页面的整体DOM结构，提取出**与 bug 相关的内容**（标题、描述、复现步骤、评论、堆栈、环境、附件说明等内容），用于后续分析。如果 `comprehend.md` 阶段因用户对 Q3 留空而把 `bug_appear_time` 暂记为“待从报告链接提取”，在本阶段打开报告链接的同一次读取中，同时提取「bug出现」「Bug 出现」「创建日期」「创建时间」「创建于」「Created」「Created Date」等字段值并更新 `bug_appear_time`；不要为了补齐时间单独提前或重复打开报告链接。

### 可行办法

**使用 Codex 插件在浏览器打开链接**

使用 Codex 的 `chrome:control-chrome` 插件的浏览器控制能力可以直接复用浏览器的现有登录态，只做只读查看，不提交任何内容。

- 适用：用户已经在本机使用 Codex 插件可控制的浏览器登录了 Jira / 禅道 / 前端监控系统。
- 优点：直接共享现有 Cookie、登录会话、已安装的扩展，不需要也不用担心网站的限制。因为对网站来说，就是用户本人在操作浏览器。
- 边界：只读取工单可见内容，不点击提交、编辑、删除、状态流转等会改变服务端数据的控件。
- Agent 动作：连接 Codex 插件的浏览器能力后，新开或复用一个标签页打开工单链接，只读取与 bug 相关的标题、描述、复现步骤、评论、堆栈、环境、附件说明等内容；若 `bug_appear_time` 处于待提取状态，同时读取报告里的时间字段并更新它，完成之后关闭标签页，回到代码分析。
- 特别处理：如果有前端监控平台的链接，对于用户操作路的径Breadcrumbs部分，要先点击页面的" Show All 100 Breadcrumbs"按钮，拿到全部的Breadcrumbs内容。
- 异常处理：如果 Codex 插件能够连接浏览器，但打开链接后页面是登录页、权限错误页、网络错误页或空白页，立即中断链接分析流程，向用户报告异常，让用户处理登录/权限/网络问题或决策下一步。

### Agent 执行要点

- 只使用 Codex 插件的浏览器登录态共享方案读取报告链接内容。
- 不主动要求用户粘贴页面内容。
- 不主动使用 API token、curl 或未文档化接口请求报告链接。
- 不主动调用 `tools/get-link-content.mjs` 抓取报告链接；该工具代码保留在仓库中，仅作为手动调试/历史兼容工具，不作为本流程的执行路径。
- 同一个报告链接在本阶段只打开一次；不要在 `comprehend.md` 阶段为了 `bug_appear_time` 提前打开，也不要在已读取完整内容后为了时间字段重复打开。
- 如果 `bug_appear_time` 处于待提取状态，但报告链接无法打开、需要登录/权限、页面为空，或没有可提取的上述时间字段，赋值 `bug_appear_time` 为今天，并在后续分析结果里说明这是兜底默认值。
- 拿到内容后：区分**事实**（链接里写的）与**推断**（从代码推出的），再进入「综合分析」。

### 用户交互

成功后，输出模板：

```
已成功获取到 ${报告链接} 里的具体信息。
```

## 综合分析

在完成「新建分支」「分析链接（如有）」之后，在此阶段**系统阅读代码与上下文**，把**现象**与**根因**对上号，为 `${actual_fix_branch}.md` 提供可落地的依据。

### 角色与边界

- 以**资深前端工程师**视角为主（熟悉现代 JS/TS/Node、浏览器行为、计算机网络、React、Vue 及常见状态/路由/请求栈），但**不要**把问题强行归因为一定是前端原因——若明显是后端、构建、原生壳、网络策略，应如实写清并调整排查重点。
- **事实**（工单/用户口述/监控/抓到的 DOM 文本）与**推断**（从代码路径推出的结论）分块写；推断须附**代码引用**。
- 本阶段不改业务代码，只查找和确定原因。

### 建议分析顺序（按需跳过不适用的步骤）

1. **对齐现象**：用 1～3 句话复述「期望 vs 实际」，与 `bug_appear_time`、`bug_appear_baseline`（基线）一致。
2. **复现路径**：从入口（路由、按钮、请求）到报错/错误 UI 的调用链；标明**是否必现**、触发条件（机型、登录态、数据条数等）。如果之前分析了前端监控平台的链接，需要根据Breadcrumbs内容，尝试复现和分析。
3. **缩小范围**：先用搜索/全局查找定位模块，再读到**具体文件与函数**；对关键分支加「为何这里会导致现象」的说明。
4. **根因假设**：可列 1～2 个备择，用证据排除；最终给出**主因**一句话 + 支撑点（堆栈、接口返回、条件判断、竞态等）。
5. **同类排查**：在仓库内检索**相同反模式**（同一 hook 误用、同一 API 封装、同一文案/判断），在结论中说明是否**仅单点**还是**一类问题**；若多处，在报告与修复阶段标明范围。
6. **与链接信息对表**：若拿过 Jira/禅道/监控内容，逐项回应：环境、版本、是否已在分析中覆盖。

### 用户交互

分析完成之后，不用复述 bug 详情，只向用户输出原因、证据链和复现路径，要求用户手动复现 bug 并询问 bug 原因是否正确，如果正确，进入下一流程；否则根据用户的回答，视情况进一步分析（分析方向正常）或者重新从头分析（分析方向错误），继续查找和确定原因。如果之前分析了前端监控平台的链接，需要对Breadcrumbs总结归纳并列出。

输出原则：

- **结论优先**：开头写「最可能根因」再给证据链。  
- **代码引用**：使用工作区要求的格式（`startLine:endLine:path`），避免无出处的文件名堆砌。  
- **阻塞显式写出**：若缺少复现、权限、接口样例，说明**缺什么**与**下一步**，不要假装已定位。  
- **禁止**：为凑结论而臆造未读过的 API/文件；大段与当前 bug 无关的泛读总结。

输出模板（没有前端监控平台链接）：

```
分析结果如下：

**原因**

${原因}

**证据链**

${证据链}

**复现**

${复现}

请你手动复现 bug，并告知我 bug 原因是否正确。
```

输出模板（有前端监控平台链接）：

```
分析结果如下：

**用户操作路径**

${对用户操作路径Breadcrumbs的总结归纳}

**原因**

${原因}

**证据链**

${证据链}

**复现**

${复现}

请你手动复现 bug，并告知我 bug 原因是否正确。
```
